# 📘 06. セッション認証と画像アップロード

― コントローラーを横断する2つの仕組みを深掘り ―

> 対応する learn：第7章_2（テンプレートとSecurityConfig）／第8章（画像アップロード対応）
> 解説対象：ログイン/ログアウトのセッション・各コントローラーの画像保存処理

---

## 🎯 6-0. この章のゴール

- このアプリの「ログイン状態」が **HttpSession の `"user"` 属性**であることを説明できる
- ログイン〜ログアウトのセッションのライフサイクルを追える
- `MultipartFile` → ファイル名生成 → `Files.copy` の画像保存フローを説明できる
- 画像保存パスの落とし穴（実行時相対パス）を理解する
- learn の Spring Security 版と、実コードのセッション版の違いを言える

---

## 🧩 6-1. このアプリの認証は「Spring Security ではない」

最初にハッキリさせます。

| 観点 | 実コード | learn 第7章_2 |
| --- | --- | --- |
| 認証の仕組み | **自前のHttpSession** | Spring Security |
| 依存 | `spring-boot-starter-security` **なし** | あり |
| ログイン判定 | `session.getAttribute("user")` が null か | `SecurityContext` / 認証フィルタ |
| URL保護 | **なし**（誰でもURLを叩ける） | `SecurityFilterChain` で保護 |
| CSRF対策 | なし | デフォルト有効 |

👉 つまり実コードは **「ログインしたら UserEntity をセッションに入れておく」だけ** のシンプルな方式。
　 URL を直接叩けば未ログインでもページに到達できてしまう（その場合は後述の NPE）。

## 🔐 6-2. ログイン状態のライフサイクル

### ① ログイン時：セッションに格納

[UserLoginController](../src/main/java/blog/ex/controller/UserLoginController.java) の `login`：

```java
UserEntity userList = userService.loginAccount(email, password);
if (userList == null) {
    return "redirect:/user/login";          // 失敗
} else {
    session.setAttribute("user", userList);  // ★ ここで“ログイン状態”が生まれる
    return "redirect:/user/blog/list";
}
```

### ② 各画面：セッションから取り出す

ログイン後のコントローラーは、毎回この1行でユーザーを復元します：

```java
UserEntity userList = (UserEntity) session.getAttribute("user");
Long userId = userList.getUserId();      // → 自分の記事だけ表示/操作するために使う
```

- `getAttribute` の戻り値は `Object` なので **`(UserEntity)` キャストが必須**。
- `userId` は「**誰の記事か**」を絞り込むキー（`findByUserId` 等）。

### ③ ログアウト時：セッションを破棄

[LogoutController](../src/main/java/blog/ex/controller/LogoutController.java)：

```java
session.invalidate();             // セッションごと無効化 → "user" も消える
return "redirect:/user/login";
```

```text
[未ログイン] ──login成功──▶ [session.user = UserEntity] ──logout──▶ [session無効化] ──▶ [未ログイン]
```

### `@Autowired private HttpSession session;` の正体

各コントローラーはセッションをフィールド注入しています。
Spring は **リクエストごとの実際の HttpSession へ橋渡しするプロキシ**を注入するため、
シングルトンのコントローラーでも、その時のユーザーのセッションを正しく扱えます。

## ⚠️ 6-3. 未ログインで来たら何が起きる？

ログイン後コントローラーには **未ログインガードがありません**。
例：未ログインで `/user/blog/list` を直接開くと——

```java
UserEntity userList = (UserEntity) session.getAttribute("user");  // null
Long userId = userList.getUserId();   // 💥 NullPointerException
```

- セッションに `"user"` が無い → `userList` が null → `getUserId()` で NPE。
- **「ログイン後にしか遷移してこない」** 前提の実装。
- 本来は「null なら `redirect:/user/login`」のガードを各所に入れるか、
  Spring Security / インターセプタで一括保護するのが定石（[09](09_learnとの対応・発展トピック.md)）。

## 🖼 6-4. 画像アップロードの仕組み

画像保存は **2箇所**で **同じコード**が使われています：

- [BlogRegisterController#blogRegister](../src/main/java/blog/ex/controller/BlogRegisterController.java)（新規登録時）
- [BlogImageEditController#blogImgUpdate](../src/main/java/blog/ex/controller/BlogImageEditController.java)（画像差し替え時）

### コード（共通部分）

```java
@RequestParam MultipartFile blogImage   // ① アップロードファイルを受け取る
...
String fileName = new SimpleDateFormat("yyyy-MM-dd-HH-mm-ss-").format(new Date())
                  + blogImage.getOriginalFilename();    // ② 保存名を作る
try {
    Files.copy(blogImage.getInputStream(),
               Path.of("src/main/resources/static/blog-img/" + fileName));  // ③ 物理保存
} catch (Exception e) {
    e.printStackTrace();    // ④ 失敗してもログだけ出して続行
}
```

### ステップ分解

| 手順 | 何をしている | 補足 |
| --- | --- | --- |
| ① 受信 | `MultipartFile` で multipart/form-data のファイル部を受ける | フォーム側は `enctype="multipart/form-data"` が必要 |
| ② 命名 | `2026-06-22-14-30-05-` + 元ファイル名 | 秒精度の日時を前置して**名前衝突を避ける** |
| ③ 保存 | `Files.copy(入力ストリーム, 保存先Path)` | `static/blog-img/` 配下に書き出す |
| ④ 例外 | `catch` で `printStackTrace` のみ | **保存失敗してもDB登録に進んでしまう** |

### 保存後の流れ

- ②で作った `fileName`（文字列）を **Service → Entity → DB** に保存。
  実ファイルは `static/blog-img/`、DBには **ファイル名だけ**が入る。
- 画面表示時は `static/blog-img/ファイル名` のURLで `<img>` 参照する（静的リソース配信）。

```text
[ブラウザ: 画像選択] ──multipart POST──▶ [Controller]
        ├─ Files.copy → static/blog-img/2026-...-焼肉.jpg（実ファイル）
        └─ createBlogPost(..., fileName, ...) → blogs.blog_image = "2026-...-焼肉.jpg"（DB）
```

## 🕳 6-5. 画像保存の落とし穴（重要）

### 落とし穴①：保存パスが「実行時ディレクトリ相対」

```java
Path.of("src/main/resources/static/blog-img/" + fileName)
```

- これは **絶対パスではなく、アプリを起動したカレントディレクトリからの相対パス**。
- `mvnw spring-boot:run` をプロジェクト直下で実行している間は動くが、
  **jar 化して別の場所から起動すると `src/main/...` が存在せず保存に失敗**する。
- そもそも「ビルド元のソースディレクトリ」に実行時データを書く設計自体が脆い。
  本番では `application.properties` に保存ディレクトリを定義し、絶対パスで外部フォルダに保存するのが定石。

### 落とし穴②：例外の握りつぶし

```java
catch (Exception e) { e.printStackTrace(); }
```

- 保存に失敗しても **処理は止まらず DB 登録に進む**。
- 結果、**「DBにはファイル名があるのに実ファイルが無い」** 不整合が起こり得る（画像リンク切れ）。

### 落とし穴③：同名・同秒の衝突

- 命名は秒精度（`HH-mm-ss`）。同じ秒に同名ファイルを2枚上げると `Files.copy` が
  `FileAlreadyExistsException` を投げる（が、②同様に握りつぶされる）。

### 落とし穴④：拡張子・サイズ・MIME 未検証

- アップロードされたファイルの種類・サイズチェックが無い。
  本番では画像以外の拒否・サイズ上限が必要。

> 📝 テストでは `MockMultipartFile("blogImage", "test-image.jpg", "image/jpeg", new byte[0])` と
> **中身が空（0バイト）**のダミーを使い、`Files.copy` が実際に走っても無害なファイルを作るだけにしている（[08](08_単体テスト解説_Controller編.md)）。

## 🖼 6-6. 「画像編集」と「テキスト編集」の役割分担

記事の更新は **2系統に分かれている**のが、このアプリの特徴です。

| 編集対象 | コントローラー | Service メソッド | 画像ファイル |
| --- | --- | --- | --- |
| タイトル・日付・カテゴリー・本文 | `BlogEditController` | `editBlogPost` | **触らない**（既存維持） |
| 画像のみ | `BlogImageEditController` | `editBlogImage` | 新規保存して名前を差し替え |

- だから `editBlogPost` は `blogImage` を set しない（[04](04_Service解説.md)）。
- `editBlogImage` は **「新しい名前のときだけ」** 更新する（同名なら `false`）。

---

## ✅ 6-7. まとめ

- 認証は **HttpSession の `"user"` 属性**に `UserEntity` を入れるだけ（Spring Security 不使用）。
- ログイン後コントローラーは毎回 `session.getAttribute("user")` でユーザー復元 → **未ログインだと NPE**。
- ログアウトは `session.invalidate()`。
- 画像は `MultipartFile` を `日時+元名` で `static/blog-img/` に `Files.copy`、DBには**ファイル名のみ**。
- 保存パスが実行時相対・例外握りつぶし・検証なし、という**学習段階の弱点**がある。
