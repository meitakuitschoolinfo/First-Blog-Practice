## 🧩 8-2. そもそも「テスト」とは何か？

### 一言で言うと

> テスト＝
> **製造したプログラムが「要件通り動くか」を検証する工程**

```text
[ プログラム ] ─── 要件通り動作するか検証 ───▶ [ テスト結果 ]
                                                      ├── OK（想定通り）
                                                      └── NG → 修正 → 再検証
```

### 開発工程の中の位置

```text
要件定義 ─▶ 基本設計 ─▶ 詳細設計 ─▶ 製造
                                       │
                                       ▼
                                   単体テスト ─▶ 結合テスト ─▶ システムテスト ─▶ 本番移行
```

👉 **「作ったもの」と「要件」は別物**。
　 テストで両者がつながっていることを確認して、初めて完成と言える。

## 🪜 8-3. テストの3階層

| 段階           | 何を検証する？                          | 対応する設計工程 | 主な実施者          |
| -------------- | --------------------------------------- | ---------------- | ------------------- |
| **単体テスト** | プログラム1つが詳細設計通り動くか       | 詳細設計         | 開発者本人          |
| **結合テスト** | 複数プログラムを連結した一連の流れ      | 基本設計         | 開発者・QA          |
| **システムテスト** | 周辺システムも含めた全体              | 要件定義         | QA・場合によりユーザー |

### この章でやるのは「単体テスト」

- **1つの Controller / Service / Repository** が、設計通りに動くか
- 他のクラスは **Mock（偽物）** に置き換えても良い
- → **小さな単位で、繰り返し、機械的に** 回せるのが特徴

## 🎭 8-4. その他のテスト

| 種類             | 目的                                                |
| ---------------- | --------------------------------------------------- |
| ユーザーテスト   | エンドユーザーによる受け入れ検証                    |
| 回帰テスト       | 修正の影響で **既存機能が壊れていないか** 確認     |
| 負荷テスト       | 性能・同時接続耐性の検証                            |
| セキュリティテスト | SQLインジェクション等の脆弱性検証                  |

👉 「単体テスト」を **自動化** しておくと、**回帰テストが秒で回る**。
　 これが「テストを自動コードで書く」最大のリターン。

## 🔬 8-5. ブラックボックス vs ホワイトボックス

### ブラックボックステスト

> **中身（実装）を見ずに、入力 → 出力 だけを見る**

- 業務要件・仕様に沿って動くかをチェック
- **結合テスト・システムテスト** で主に使う
- 設計技法：**観点整理 / 同値分割 / 境界値 / デシジョンテーブル**

### ホワイトボックステスト

> **コードの全経路を通るようにケースを作る**

- if/for の分岐網羅
- **単体テスト** で主に使う
- 設計技法：**直交表 / All-Pair法**

👉 この章では **両方を意識** する：
　 ・Controller の単体テストは仕様（URL・期待画面）ベース＝ブラックボックス寄り
　 ・Service の単体テストは分岐網羅＝ホワイトボックス寄り

## 📐 8-6. テストケース設計の流れ

```text
[テスト観点作成] ─▶ [テラーリング] ─▶ [具体的なケース設計]
       │                  │                    │
   PJ全体で必要な       テスト対象機能で      対象機能ごとに
   観点を整理する       必要な観点だけ        境界値など具体値
   （標準テンプレ）     ピックアップ          を設計
```

### テスト観点（例）

| テスト種別 | 大分類   | 中分類 | 小分類             | 目的                                 |
| ---------- | -------- | ------ | ------------------ | ------------------------------------ |
| 入力チェック | 正常系 | 検索   | 単項目検索         | 1つの検索条件のみで検索実行          |
| 入力チェック | 異常系 | 共通   | 必須チェック       | 必須項目で未入力がエラーになることを確認 |
| 入力チェック | 異常系 | 文字列 | 文字列長チェック   | 最大桁数を超えるとエラーになる確認   |
| 入力チェック | 異常系 | 日付   | 日付形式チェック   | 既定形式以外でエラーになる確認       |

### 同値分割

> **同じ結果になる値の群（同値クラス）から1つだけ代表値を選ぶ**

| 入力値 | 挙動    |
| ------ | ------- |
| 負の値 | エラー  |
| 小数   | エラー  |
| 0      | A       |
| 1〜99  | B       |
| 100以上| C       |

→ 5つの同値クラスから **代表値（-1 / 0.5 / 0 / 50 / 100）** だけ選ぶ。
　 「全部の値を試す」のは不可能なので、**代表値で十分** という発想。

### 境界値分析

> **境界の前後にバグが多い** という経験則から、**onポイント / offポイント** を必ず試す

```text
1文字以下 │ 2文字〜50文字 │ 51文字以上
  ✗         ✓               ✗
  ↑         ↑    ↑          ↑
  1(off)    2(on) 50(on)    51(off)
```

- **onポイント**：有効同値クラスの最小値・最大値（境界そのもの）→ 必ず試す
- **offポイント**：その隣の無効値 → 必ず試す
- 結果：`1` / `2` / `50` / `51` の **4ケース**（境界周辺だけで判定）

👉 **「同値分割でケース数を減らす → 境界値で抜けを潰す」** が王道。

## 🧪 8-7. なぜ Spring Boot の世界では **テストを「コードで書く」** のか？

### 手動テスト vs 自動テスト

| 観点                      | 手動テスト       | 自動テスト（JUnit）        |
| ------------------------- | ---------------- | -------------------------- |
| 1回目の実行コスト         | 低い             | 高い（コードを書く）       |
| 100回目の実行コスト       | **100倍かかる**  | **ほぼゼロ**（再実行だけ） |
| 漏れ                      | 人間ミスあり     | 書いた分は確実に再実行     |
| デプロイ前のセーフティネット | 構築困難       | CI で自動                  |

→ 「修正したら壊れていないか不安」を、**`mvn test` 1コマンドで自動検証**。
　 これがある＝ **安心して直せる** ＝ **コードがしぬほど書きやすくなる**。

### 単体テストコードの3つのレイヤー（Spring Boot 4.x）

| アノテーション      | 何を起動するか                       | 用途                          | 速度    |
| ------------------- | ------------------------------------ | ----------------------------- | ------- |
| `@SpringBootTest`   | **アプリ全体**（DB含む）            | E2E / 結合テスト              | 遅い    |
| `@WebMvcTest`       | **Controller周辺のみ**（DB無し）    | Controller単体（MockMvc併用） | 中      |
| `@DataJpaTest`      | **JPA + 組込DB のみ**                | Repository単体                | 中      |
| （素のJUnit + Mockito）| **何も起動しない**                  | Service / 普通のクラス単体    | 高速    |

👉 **テストするクラスに必要な最小限だけ起動する** のがコツ。
　 全部 `@SpringBootTest` にすると、数百個のテストで1時間かかる地獄に。

## 🔧 8-8. Spring Boot 4.x のテスト主要登場人物

### `MockMvc`

- HTTPリクエストを **「実際にネットワーク経由で送らずに」** Controllerに渡せる Spring の道具
- レスポンスのURL・テンプレート名・モデル属性・HTTPステータスなどを **fluent API** で検証できる

```java
mockMvc.perform(get("/blogs"))           // GET /blogs を実行
    .andExpect(status().isOk())          // 200 が返る
    .andExpect(view().name("blog/list")) // テンプレートが blog/list
    .andExpect(model().attributeExists("page"));
```

### `@MockitoBean` （Spring Boot 3.4+ / 4.x の新標準）

- Spring の DI コンテナに **「偽物（Mock）の Bean」** を差し込む
- 実 DB を呼びたくないとき、Repository を Mock 化して Service だけテストする

```java
@MockitoBean
private UserRepository userRepository;
```

> ⚠️ Spring Boot 4.x では旧 **`@MockBean`** は廃止予定。**`@MockitoBean`** を使う。

### Mockito 基本3行

```java
// Mockがどう返すか定義
when(userRepository.findByEmail("ake@test.com"))
    .thenReturn(Optional.of(someUser));

// テスト対象を呼ぶ
User result = userService.findByEmail("ake@test.com");

// 結果を検証
assertThat(result.getName()).isEqualTo("Akemi");
```

### AssertJ vs JUnit Assertions

- **AssertJ** （`assertThat(actual).isEqualTo(expected)`）：流暢で読みやすい / 推奨
- **JUnit Assertions** （`assertEquals(expected, actual)`）：素朴 / 古くから

本研修は **AssertJ** を採用します。

## 🅰️ 8-9. ★最重要★ AAA パターン（Arrange / Act / Assert）

すべての単体テストは **3ブロック構成** で書くと読みやすい：

```java
@Test
void test_メソッド名_条件_期待結果() {
    // ───── Arrange（準備） ─────
    // 入力値・モックの戻り値などをセット
    User user = new User();
    user.setEmail("ake@test.com");
    when(userRepository.findByEmail("ake@test.com")).thenReturn(Optional.of(user));

    // ───── Act（実行） ─────
    // テスト対象のメソッドを1回だけ呼ぶ
    User result = userService.findByEmail("ake@test.com");

    // ───── Assert（検証） ─────
    // 結果が期待通りか確認
    assertThat(result.getEmail()).isEqualTo("ake@test.com");
}
```

### テストメソッドの **命名規則**

| 形式                                      | 例                                                  |
| ----------------------------------------- | --------------------------------------------------- |
| `テスト対象_条件_期待結果`                | `findByEmail_存在するemail_Userを返す`              |
| `テスト対象_条件_期待結果`                | `register_重複emailの場合_IllegalArgumentException` |

👉 **メソッド名だけで「何をテストしているか」が分かる** ことが最重要。

## 📋 8-10. ★最重要★ 単体テスト仕様書とテストコードの関係

### 仕様書見本（PDF p.30 添付）の構造

```
┌─────────────────────────────────────────────────────────────┐
│ システム名 / サブシステム名 / 作成者 / 作成日 / 実施者       │
├──┬──────────┬───────────────┬─────────────┬──────┬────┬───┤
│No│ 分類     │ テスト項目    │ 検証内容    │実施日│結果│備考│
├──┼──────────┼───────────────┼─────────────┼──────┼────┼───┤
│1 │表示テスト│ /login GET    │ view=login  │      │    │   │
│2 │email入力 │ 正しい組合せ  │ /admin/blogs│      │    │   │
│..│..        │..             │..           │..    │..  │.. │
└──┴──────────┴───────────────┴─────────────┴──────┴────┴───┘
```

### 仕様書 → テストコード の **1対1対応**

| 仕様書                                 | テストコード                                        |
| -------------------------------------- | --------------------------------------------------- |
| **No / テスト項目**                    | `@Test` メソッド1個                                 |
| **分類** （表示/入力値/異常）          | `@Nested` クラス または DisplayName                |
| **検証内容**                           | `.andExpect(...)` の連なり                          |
| **結果（OK/NG）**                      | `mvn test` の結果                                   |

👉 **仕様書1行 = テストメソッド1個** が基本対応。
　 仕様書を見ながらコードを書く → コードを見ながら仕様書を埋める、の往復で抜けが減る。

## 📝 8-12. ★最重要★ ソースを書く順番（単体テストの作法）

### 機能1つ分の「テスト製造フロー」

```text
[1] 仕様書を書く（Markdown）
       │
       ▼
[2] テストクラスの骨組みを作る（@SpringBootTest 等のアノテーション）
       │
       ▼
[3] 依存先のモック宣言（@MockitoBean）
       │
       ▼
[4] 仕様書のNo順に @Test メソッドを生やす（空でOK）
       │
       ▼
[5] 各メソッドの中を AAA で埋める
       │
       ▼
[6] mvn test を回す → 仕様書の「結果」列にOK/NG
       │
       ▼
[7] NGなら本体コード or テストコードを修正
```

### この章での書く順番（ログイン機能）

| 順番 | 作るもの                                  | 理由                                         |
| ---: | ----------------------------------------- | -------------------------------------------- |
|    1 | `UnitTestSpecification/04_ログイン機能_仕様書.md` | **先に仕様書を書く** → 何を確認するか確定 |
|    2 | `UserServiceTest.java`                    | **下から先**：Service層の単体テスト          |
|    3 | `LoginControllerTest.java`                | **上に進む**：Controller層 + Security        |

### なぜ Service テスト → Controller テスト の順か？

- Controller は Service を呼び出す
- → Service の挙動が確定してから Controller のテストを書くと、**ど ちらが原因の失敗か** 切り分けやすい
- → 失敗時の原因切り分けは「下から順に詰めた」方が圧倒的に楽

## ✨ 8-13. ソースを書くときのポイント（必読）

### ポイント①：**1テスト＝1検証**

```java
// ❌ NG：何個も assert を入れる
@Test
void allInOne() {
    // login テスト
    // logout テスト
    // ...
}

// ⭕ OK：分割
@Test void showLoginForm_GET_loginテンプレートを返す() { ... }
@Test void doLogin_正しい認証情報_管理画面にリダイレクト() { ... }
@Test void doLogin_間違ったパスワード_エラー画面にリダイレクト() { ... }
```

### ポイント②：**テストの中で if / for を書かない**

- テスト中に分岐が出てきたら、それは **2つのテストに分けるサイン**
- 分岐を含むテストは **読めない / 落ちたとき原因が追えない**

### ポイント③：**Mock の戻り値は「最小限」**

```java
// ❌ NG：使わないメソッドまでモック
when(repo.findAll()).thenReturn(...);   // このテストで使わない

// ⭕ OK：今のテストで呼ばれるメソッドだけ
when(repo.findByEmail("ake@test.com")).thenReturn(...);
```

### ポイント④：**期待値はテスト内に直書き**

定数を外に出すと、**テストが「何を期待しているか」分かりにくくなる**。

```java
// ⭕ OK：直書き
assertThat(user.getEmail()).isEqualTo("ake@test.com");

// ❌ NG：定数化（Production側と一緒にしてしまうのは特にNG）
assertThat(user.getEmail()).isEqualTo(EMAIL_AKEMI);
```

### ポイント⑤：**MockMvc では `csrf()` を忘れない**

Spring Security 有効時、POST テストでは CSRF トークンが必要：

```java
mockMvc.perform(post("/login")
    .param("email", "...")
    .param("password", "...")
    .with(csrf()))   // ← 忘れると 403
    .andExpect(...);
```

### ポイント⑥：**Security 適用環境では `@WithMockUser` か `@WithAnonymousUser`**

```java
@Test
@WithMockUser              // 認証済みとして振る舞う
void edit画面_認証済み_表示OK() { ... }

@Test
@WithAnonymousUser         // 未認証として振る舞う
void edit画面_未認証_loginに飛ばされる() { ... }
```

### ポイント⑦：**テストデータは「最小限・分かりやすく」**

- 仕様書の例値（`ake@test.com` / `1234abcd`）を **そのまま使う**
- 仕様書とコードで値が違うと、後で混乱する元

### ポイント⑧：**仕様書の "結果" 列は最初は空のまま**

- 仕様書を書いた段階では、まだコードが正しいか分からない
- `mvn test` が緑になってから "OK" を埋める
- → これが **「テストが仕様の証拠」になる** 流れ

## ❌ 8-14. 初心者がやりがちなNG

| NGパターン                                    | 何が起きる？                                       |
| --------------------------------------------- | -------------------------------------------------- |
| `@SpringBootTest` を全テストに付ける          | テストが遅すぎて誰も実行しなくなる                 |
| 旧 `@MockBean` を使う（Spring Boot 4.xでは廃止）| コンパイル警告 or 動かない                        |
| MockMvc POST に `.with(csrf())` を忘れる      | 全部 403 で原因が分からず詰まる                   |
| テスト内で本物の DB / メール送信を呼ぶ        | テストが環境依存になり、CIで壊れる                 |
| テストメソッド名を `test1` `test2` にする     | 失敗ログを見ても何が壊れたか分からない             |
| 1メソッドに10個 assert を詰める               | どこで失敗したか追えない / 落ちたら芋づる的に修正  |
| 仕様書を書かずにテストコードだけ書く          | 観点漏れに気づけない / 仕様変更に追従できない      |
